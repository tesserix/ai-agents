# Review planning preparation once with the final itinerary

Two concurrent production mobile requests on 2026-10-13 exceeded the synchronous planner deadlines after the grounding and budget fixes. Gateway timings included a 38-second request review with only 40 output tokens. The pipeline could make nine initial model calls: three for planning and three each for weather and entry preparation. The advisory workers already return every eligible provider record unchanged, regardless of model selection. Their recursive reviews frequently hit their 25-second deadlines and discarded available preparation information.

For three-option planning only, project current weather and entry records directly into preparation summaries. Preserve all source URLs, coverage gaps, missing traveller fields and verification states. Do not manufacture visa eligibility or forecasts. Retain the independent request-compatibility review and final itinerary review. The final reviewer receives both preparation summaries and their complete provider evidence; a rejected final verdict still prevents any answer reaching the user. Standalone weather and entry requests retain their current specialist workflow.

This reduces initial model calls from nine to three without changing endpoint contracts, deadlines, storage, authentication, delegation or replica counts. Existing bounds remain: 40 evidence records, 40 KB review context, 64 KB worker reply, 80-second manager request and 95-second mobile request. Qualification uses two concurrent synthetic requests because two simultaneous mobile failures are the observed load; peak production RPS and p99 are not yet measured. No data volume or 12/36-month storage growth is introduced. Target remains completion within the current mobile deadline while preserving fail-closed final approval. Provider outages retain explicit unavailable preparation summaries.

An isolated lower-reasoning trial took 53 seconds versus 52 seconds for the existing configuration, so that tuning is not deployed. Increasing all timeouts was rejected because the public edge has a roughly 100-second limit. This change saves up to six model calls per plan with no new recurring infrastructure cost. Deployment uses a reviewed immutable manager image through GitOps; reverting that pin restores the old workflow without a schema migration.

A concurrent Sydney evaluation also reproduced an invalid allocation after the planner had used its second call repairing grounding. Replace the additional model budget-repair definition with integer allocation resizing. Only invalid tiers are processed: retain affordable increasing totals where possible, otherwise use the existing 60/80/95 percent ceiling targets. Preserve each option's relative non-contingency category weights using exact integer apportionment, reserve at least 10 percent for a resized tier's contingency, and keep every itinerary stop unchanged. Reject empty category weights and ceilings too small for distinct targets. These values remain explicitly unverified spending allocations, not researched prices or quotes; annotate adjusted responses and send them through the same final independent review. Do not resize evidence prices or bypass feasibility review. This removes a model call and an entire repair definition while retaining the two-call cap for actual itinerary grounding.

A Sydney candidate still took 80.55 seconds including 8.7 seconds of evidence collection, 7.2 seconds of request review, 40.7 seconds of draft generation and 24 seconds of final review. For read-only three-option planning, overlap request review and signed draft generation after authentication, profile binding, required-detail checks and evidence validation. Await request approval before consuming the draft, then perform the unchanged independent final review. Cancel and await the draft when request review rejects or the request is cancelled. Other specialists remain sequential. The critical path becomes evidence + max(request review, draft) + final review, saving the request-review duration without extending deadlines. No draft is returned or persisted on rejection. A rejected request may consume one bounded speculative model call, but cannot book, write files or mutate a trip. Regression tests verify overlap, rejection, cancellation and the two distinct review records.
